## 3. models 和 schemas 的区别

**models 描述数据库怎么存；schemas 描述接口收什么、如何校验。** 当前 schemas 主要定义请求格式，也可以用于响应，但当前代码大多显式返回字典。

| 对比 | models | schemas |
| --- | --- | --- |
| 基类 | SQLAlchemy 的 `Base` | Pydantic 的 `BaseModel` |
| 核心内容 | 表名、列类型、主键、外键、唯一约束 | 字段类型、长度、默认值、固定选项、校验器 |
| 是否直接对应表 | 是 | 不一定 |
| 是否自动查询或保存 | 不会；需通过会话执行 | 不会 |
| 本项目示例 | `User`、`Question` | `UserCreate`、`QuestionCreate` |

注册时：

```text
JSON 中的 password
    ↓ UserCreate 检查长度
接口计算密码哈希
    ↓ 创建 User 对象，填写 password_hash
数据库保存 users 记录
```

请求里不需要用户 ID，也不允许通过注册自行选择管理员角色；数据库却需要保存 ID、密码哈希和角色。这就是两个模型不能混为一份的原因。

## 5. backend/database.py：数据库基础

### 5.1 读取配置

```python
PROJECT_ROOT = Path(__file__).resolve().parent.parent
load_dotenv(PROJECT_ROOT / ".env")
```

`__file__` 是当前文件路径。两个 `parent` 从文件定位到项目根目录，避免依赖启动终端的当前位置。

`load_dotenv()` 将配置加载到进程环境中；`os.environ["DB_USER"]` 再读取指定配置。缺少必要配置时会报错，而不是自动使用不明确的连接信息。

### 5.2 构造连接地址

```python
database_url = URL.create(
    drivername="mysql+aiomysql",
    # 其余账号、密码、地址等从环境变量读取
)
```

`mysql` 是数据库类型，`aiomysql` 是异步驱动。使用 URL 对象避免密码中的特殊字符影响手动拼接的 URL。

端口读出来是字符串，因此当前代码通过 `int(...)` 转为整数。

### 5.3 创建异步引擎

```python
async_engine = create_async_engine(
    database_url,
    echo=False,
    pool_pre_ping=True,
    pool_size=5,
    max_overflow=5,
)
```

引擎是连接管理入口，创建时通常还未建立实际连接。

| 参数 | 作用 |
| --- | --- |
| `echo=False` | 不输出完整 SQL 日志 |
| `pool_pre_ping=True` | 取用已有连接时检查有效性 |
| `pool_size=5` | 最多保留 5 条常规池连接 |
| `max_overflow=5` | 高峰时最多额外创建 5 条临时连接 |

不是启动就创建 10 条连接。连接按需建立，用完通常归还池中。

### 5.4 创建会话工厂

```python
AsyncSessionLocal = async_sessionmaker(
    bind=async_engine,
    expire_on_commit=False,
)
```

工厂用于创建会话，不是某一次会话。`expire_on_commit=False` 表示提交后不自动让已加载对象属性过期，当前代码提交后直接读取对象属性会更方便。

### 5.5 提供 get_db 依赖

```python
async def get_db():
    async with AsyncSessionLocal() as session:
        try:
            yield session
        except Exception:
            await session.rollback()
            raise
```

流程：

1. 为请求创建一个会话。
2. `yield session` 把会话交给接口，并暂停在这里。
3. 依赖结束时退出 `async with`，关闭会话并释放连接占用。
4. 有异常传播回来时先回滚，再用 `raise` 继续抛出。

正常结束不自动提交，写入业务代码需要明确调用 `commit()`。

### 5.6 模型基类

```python
class Base(DeclarativeBase):
    pass
```

模型继承同一个 Base，SQLAlchemy 才能统一登记映射信息。当前项目手动执行 SQL 建表，没有使用 Alembic 或启动自动建表；修改模型不会自动修改实际表。

### 5.7 四个容易混淆的对象

| 名称 | 含义 |
| --- | --- |
| `async_engine` | 管理连接池 |
| `AsyncSessionLocal` | 创建会话的工厂 |
| `get_db` | 为接口提供、清理会话的函数 |
| 接口里的 `db` | 本次请求实际使用的 AsyncSession 对象 |

数据库会话是数据库操作的工作单元，不是登录状态，也不是未来的一次面试练习。

## 6. backend/models/users.py：用户表

```python
class User(Base):
    __tablename__ = "users"
```

类对应表，一个查询到的 User 对象对应具体用户记录。

```python
username: Mapped[str] = mapped_column(
    String(50), nullable=False, unique=True
)
```

- `username`：属性名，默认也是列名。
- `Mapped[str]`：映射属性的 Python 类型。
- `String(50)`：数据库字符串长度。
- `nullable=False`：不允许 NULL，但仍需业务逻辑拒绝空白用户名。
- `unique=True`：数据库保证用户名不能重复。

`User` 是模型类；`user` 通常是查询得到的具体用户对象。登录验证必须读取 `user.password_hash`，不能把模型类上的属性描述当成用户的真实密码哈希。

`id` 是稳定身份标识，不要求连续。token 引用用户 ID，因此不能为了排序随意重排主键。

## 7. backend/models/job_roles.py：岗位

`JobRole` 对应 `job_roles`，保存岗位编号和名称，例如 Python 后端、AI 应用开发。

关键字段是整数主键和唯一的名称。统一保存名称后，多道题通过岗位 ID 关联，不需要重复写岗位名称。

这里的“岗位”与用户的 `role` 不同：前者是面试方向，后者是访问权限。

## 8. backend/models/knowledge_points.py：知识点

`KnowledgePoint` 对应 `knowledge_points`，保存 Python 基础、FastAPI、LangChain 等分类。

每个知识点有固定 ID 和唯一名称。题目按 ID 关联，未来资料、薄弱点和复习也可以复用同一分类。

当前岗位和知识点提供查询接口，管理页面没有完整实现这两类基础数据的增改停用功能。

## 9. backend/models/questions.py：题目及关系

### 9.1 Question

| 字段 | 业务含义 |
| --- | --- |
| `content` | 提问正文 |
| `difficulty` | basic 基础、advanced 进阶 |
| `reference_points` | 回答应覆盖的要点 |
| `common_mistakes` | 常见错误 |
| `followup_direction` | 追问方向 |
| `sources` | 来源标题与链接文本 |
| `status` | draft、approved、disabled |
| `revision` | 修订编号 |

`Text` 用于较长文本。`Mapped[str | None]` 配合 `nullable=True` 表示允许为空，读取为 Python 的 None。

模型中的 `default` 是 SQLAlchemy 插入时使用的默认值，不等于它主动修改了实际数据库的默认约束。

题目的来源文本并不是检索索引，目前没有自动抓取链接、切分资料或生成向量。

### 9.2 QuestionJobRole：题目与岗位

```python
question_id: Mapped[int] = mapped_column(
    ForeignKey("questions.id"), primary_key=True
)
job_role_id: Mapped[int] = mapped_column(
    ForeignKey("job_roles.id"), primary_key=True
)
```

从代码可以直接读出外键方向：

| 外键列（当前表） | 引用目标 |
| --- | --- |
| `question_job_roles.question_id` | `questions.id` |
| `question_job_roles.job_role_id` | `job_roles.id` |

例如保存 `(10, 2)`，必须先有题目 10 和岗位 2。

两列共同组成联合主键，防止同一组合重复；并不是每列各自唯一，因此允许 `(10, 1)` 和 `(10, 2)` 同时存在。

一列可以同时是外键和联合主键的一部分。外键保证引用存在；联合主键保证关联不重复。

### 9.3 QuestionKnowledgePoint：题目与知识点

同理：

- `question_knowledge_points.question_id` 引用 `questions.id`。
- `question_knowledge_points.knowledge_point_id` 引用 `knowledge_points.id`。

这两类关系都是多对多：一道题适用多个岗位、考查多个知识点；一个岗位或知识点也对应多道题。

当前未定义 ORM 的 relationship，接口显式读写关联表。外键也不会自动帮管理员选择适合的岗位或检查题目事实正确性。

## 10. backend/schemas/users.py：用户输入

| 类 | 输入与用途 |
| --- | --- |
| `UserCreate` | 注册：用户名、密码、昵称 |
| `UserLogin` | 登录：用户名、密码 |
| `UserNicknameUpdate` | 修改昵称：仅昵称 |

当前规则：用户名 1～20 字符，密码 6～20 字符，昵称最多 20 字符。这是现有开发规则，不代表部署所需的全部账号安全策略。

```python
nickname: str = Field(default="", max_length=20)
```

允许省略昵称，使用空字符串。

```python
nickname: str = Field(max_length=20)
```

必须提交 nickname 字段，但允许空字符串，用于清空昵称。

Schema 不能单凭长度规则判断用户名是否重复、密码是否正确；这些要查询数据库和执行业务验证。

## 11. backend/schemas/questions.py：题目输入

### 11.1 QuestionCreate

当前正文、参考要点和可选文本的最大长度均为 1000 字符。

```python
difficulty: Literal["basic", "advanced"] = "basic"
job_role_ids: list[int] = Field(min_length=1)

Literal 限制固定值；列表至少包含一个编号。编号是否真实存在由后端查询校验。

@field_validator("content", "reference_points")
@classmethod
def check_not_blank(cls, value: str):
    value = value.strip()
    if not value:
        raise ValueError("内容不能为空或全是空格")
    return value
```

拒绝纯空白正文和参考要点。`cls` 表示模型类，`value` 是当前字段值，返回值是校验后的内容。

### 12.2 健康检查

/health 返回固定消息；/health/db 执行：

```python
result = await db.execute(text("SELECT DATABASE()"))
database_name = result.scalar_one()
```

text 包装 SQL，execute 执行查询，scalar_one 要求一行并取第一列。正常得到 ai_interview 证明该次数据库查询成功。

### 12.3 register：注册

```text
Schema 校验 → 去除用户名首尾空格 → 拒绝空白
    → 查询是否重复 → 密码哈希 → 创建 User
    → add → commit → 返回公开信息
```

```python
hashed_password = await run_in_threadpool(
    password_hasher.hash, data.password
)
```

密码哈希是计算工作，在线程中执行，避免阻塞异步事件循环。不是可逆加密。

查询查重用于友好反馈，唯一约束处理并发注册的最终冲突。`IntegrityError` 中 MySQL 错误码 1062 表示重复键。

注册角色固定为 user，不能由前端自行指定 admin。

### 12.4 login：登录与 JWT

查询用户后验证 `data.password` 与 `user.password_hash`。失败统一返回“用户名或密码错误”。

```python
payload = {
    "sub": str(user.id),
    "exp": datetime.now(timezone.utc) + timedelta(days=7),
}
token = jwt.encode(payload, JWT_SECRET_KEY, algorithm="HS256")
```

- token 就是令牌的英文。
- sub 保存用户编号字符串。
- exp 表示七天后过期。
- JWT_SECRET_KEY 留在后端，用于签发和验证签名。
- token 中不包含密钥；载荷可以读取，签名不等于加密。
- 当前不把 token 保存到数据库。

返回的 token_type=bearer 告诉客户端使用方式。后续请求头是：

```http
Authorization: Bearer <token>
```

HS256 使用同一秘密密钥签发和验证。更换密钥会使旧签名无法通过；用户名、密码、数据库连接密码都不是这把密钥。

### 12.5 get_current_user：识别当前用户

`HTTPBearer(auto_error=False)` 提取凭证，不负责 JWT 签名验证。没有凭证由函数统一返回 401。

```python
payload = jwt.decode(
    credentials.credentials,
    JWT_SECRET_KEY,
    algorithms=["HS256"],
    options={"require": ["sub", "exp"]},
)
```

固定算法、验证签名与有效期、要求必要字段。然后将 sub 转为整数，按主键查用户，确认账号存在。

`credentials.credentials` 是提取出的 token 字符串；重复的名字并不表示有两份 token。

当前每次查询数据库角色，因此管理员角色变化可以在后续请求中生效，无需把角色硬编码到 token。

### 12.6 Depends 与管理员检查

```python
current_user: User = Depends(get_current_user)
```

FastAPI 在执行接口前解析依赖，把返回的用户对象传入。依赖函数写名字，不加括号，因为由框架负责调用。

`get_admin_user` 再检查 `current_user.role == "admin"`。认证失败返回 401，已登录但权限不足返回 403。

```python
dependencies=[Depends(get_admin_user)]
```

表示只执行检查，不需要接收结果。即使函数体没读取 admin_user，参数依赖仍有作用。

### 12.7 read_me 和 update_nickname

read_me 明确选择返回 ID、用户名、昵称、角色，不直接返回整个用户对象，以免泄露密码哈希。

修改昵称：

```python
current_user.nickname = data.nickname.strip()
await db.commit()
```

对象已在会话中，修改属性会被跟踪，不需要再次 add。FastAPI 默认复用同一次请求中的相同 get_db 依赖，所以查询用户和提交修改使用同一会话。

接口不接收任意用户 ID，目标由 token 决定。

### 12.8 岗位、知识点查询

```python
result = await db.execute(select(JobRole).order_by(JobRole.id))
job_roles = result.scalars().all()
```

select 构造查询，order_by 指定排序；scalars 取每行第一项，这里是模型对象；all 收集全部结果。最终转成 id、name 字典列表。

当前两个接口允许匿名查询基础分类，不代表管理题目也允许匿名。

### 12.9 save_question 与 create_question

create_question 是 HTTP 入口，负责请求解析和权限检查；save_question 是可复用的内部保存函数，接收已校验的数据与会话。

```text
编号去重 → 检查岗位存在 → 检查知识点存在
    → 创建 Question → flush 获得题目 ID
    → 写岗位关联 → 写知识点关联 → commit
```

`set(...)` 去重，避免联合主键冲突。

`select(JobRole.id).where(JobRole.id.in_(job_ids))` 查实际存在的编号，与提交集合比较，发现无效编号就拒绝。

保存函数固定状态 draft、修订号 1。只有最后 commit 才提交题目及全部关联，失败时可以整体回滚。

**业务函数本身不检查管理员，必须从有权限保护的入口调用。**

### 12.10 list_questions：分页和筛选

用 conditions 收集难度、状态等条件，`where(*conditions)` 将它们逐个传入并同时满足。

岗位、知识点通过子查询查关联题目 ID，再用 Question.id.in_ 限定题目；不会因一道题有多个关联而重复返回。

```python
.offset((page - 1) * page_size).limit(page_size)
```

第 1 页跳过 0 条，第 2 页跳过一页数量。另一次 count 查询计算筛选后的总数，不受分页影响。

Query 的 ge、le 限制页码和页大小；page_size 默认 10，最大 50。

### 12.11 get_question：详情和联表

先按主键查询题目，不存在返回 404。再通过：

```python
select(JobRole).join(
    QuestionJobRole,
    JobRole.id == QuestionJobRole.job_role_id,
)
```

查关联岗位，并限定当前 question_id。知识点同理。返回完整参考内容，因此限定管理员。

### 12.12 update_question：完整替换

先查题目和校验关联编号，然后覆盖题目字段；删除旧关联再插入新关联，最后统一提交。

```python
question.status = "draft"
question.revision += 1
```

编辑后需要重新审核；ID 不变。可选字段省略会清空，难度省略使用 schema 默认值，不能把此接口当成只改一个字段的 PATCH。

当前未实现多人编辑冲突检查。revision 只是变化标记，也没有自动保存旧版本全文。

### 12.13 update_question_status：审核和停用

状态确实变化时才更新、增加 revision 并提交。draft 不参与选题，approved 才允许进入未来题池，disabled 表示停用。

状态接口保存的是管理员决定，不会自动核实参考答案或来源真实性。

### 12.14 import_questions：逐条批量导入

```python
items: list[Any] = Body(min_length=1, max_length=100)
```

先接收列表，再逐条 `QuestionCreate.model_validate(item)`，避免一条格式错误就提前拒绝全部数据。

`enumerate(items, start=1)` 的 index 是文件中的第几道，不是数据库 ID。

每道调用 save_question 单独提交。ValidationError 记录字段错误；HTTPException 记录关联编号等业务错误；SQLAlchemyError 回滚当前条并记录数据库失败。

HTTP 200 表示处理完成，各题是否成功仍看 results。重复文件会重复新增，没有自动去重或导入幂等。

## 14. frontend/app.py：用户页面入口

### 14.1 登录状态

```python
if "token" not in st.session_state:
    st.session_state.token = None
```

只初始化一次，避免每次运行都清除 token。没有 token 显示登录注册；已有 token 显示个人操作。

session_state 保存当前 Streamlit 会话的状态，不是永久数据库，页面刷新或连接重建可能需要重新登录。

### 14.2 表单与 HTTP

st.form 将输入集中到提交时处理。登录 POST /users/login，注册 POST /users/register。

```python
st.session_state.token = response.json()["token"]
st.rerun()
```

登录成功保存 token，再从头执行脚本，切换到已登录区域。注册不会自动取得登录 token。

HTTP 请求是在 Streamlit 的 Python 进程发出，不是浏览器直接执行 JavaScript fetch。

### 14.3 个人信息、昵称、退出

GET /users/me 查询信息；PATCH /users/me 提交昵称并携带 token。401 清理凭证并回登录页面。

退出只清除页面 token，不会在后端撤销旧 token，旧凭证到期前仍可能有效。

### 14.4 管理员入口

查询 /users/me 读取 role，为 admin 才调用 show_question_admin。这个显示逻辑不能替代后端授权检查。

当前为了保持简单，“查看我的信息”和管理员入口会分别查询用户，存在重复请求，但不影响基本业务。

## 17. 三条完整业务链路

### 17.1 注册

```text
app.py 表单
    → POST /users/register
    → UserCreate 校验
    → register 查重、计算哈希
    → User 对象
    → get_db 提供会话，add + commit
    → MySQL users
    → 返回成功，页面提示
```

### 17.2 管理员新增题目

```text
question_admin.py 表单
    → JSON + Bearer token
    → POST /questions
    ├── QuestionCreate 校验数据
    ├── get_current_user 验证 token 并查用户
    └── get_admin_user 检查角色
    → save_question
    → 校验分类 ID
    → questions 插入，flush 获取 ID
    → 两张关联表插入
    → commit
    → 返回题目 ID
```

### 17.3 批量导入

```text
选择 JSON 文件
    → 前端解码和检查外层结构
    → POST /questions/import
    → 验证管理员
    → 循环：逐条 model_validate → save_question → commit
        └── 某条失败：记录原因，必要时 rollback
    → 返回成功数、失败数、逐条结果
```

## 18. 常用语法速查

| 写法 | 当前项目中的含义 |
| --- | --- |
| async def | 定义异步函数，内部可等待异步操作 |
| await | 等待可等待对象，不会把同步函数自动变异步 |
| db.add(...) | 登记对象，不加 await |
| await db.execute(...) | 执行数据库语句 |
| await db.flush() | 发送待处理变更但不提交 |
| await db.commit() | 提交事务 |
| await db.rollback() | 撤销未提交变更 |
| scalar_one_or_none() | 零行返回 None，一行返回第一项，多行报错 |
| scalars().all() | 收集每行第一项，查询模型时得到对象列表 |
| select(...).where(...) | 构造条件查询 |
| join(...) | 联表匹配 |
| in_(子查询) | 限定编号属于子查询结果 |
| Depends(...) | 由 FastAPI 管理依赖解析 |
| yield | 交出值并暂停，之后继续执行清理 |
| Literal | 限定固定值 |
| Field | 设置字段校验和默认值 |
| HTTPException | 返回指定业务错误状态 |
| try / except / finally | 尝试执行、处理异常、保证清理 |
| None | 没有值，数据库可对应 NULL |
| set(...) | 去重集合 |
| enumerate(..., start=1) | 同时取元素和从 1 开始的序号 |

## 19. 当前边界与后续事项

已完成的是两个模块的基础流程，不等于所有生产要求和完整需求均已验收。

- 岗位和知识点目前主要靠基础数据准备，尚无完整维护界面。
- 题目修订号没有并发冲突保护，也没有完整历史版本记录。
- 题目批量导入没有去重、幂等和持久任务结果，断连后要先核对。
- 批量导入捕获数据库异常后尚未记录详细日志，当前错误提示却要求查日志，这是待补的小缺口。
- 没有自动事实审核；approved 是人工审核决定。
- 没有资料检索系统，sources 只是来源文本。
- 当前以人工操作验证为主，本文不宣称完成所有自动化和权限交叉验收。
- 业务主要集中在 main.py，当前便于学习，后续变大时再按需拆路由与业务函数。
- 面试会话、题目快照、回答、AI 点评等尚待开发；不要把给过的建表方案当成已完成代码。
- 后续真实练习选题必须只使用 approved 题目，并保存题目快照，避免题库修改影响历史记录。

读任何一个功能，都可以追踪五件事：**输入来自哪里、谁校验格式、谁校验权限、哪里提交数据库、结果返回给谁。**
